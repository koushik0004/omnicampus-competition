# Competition Goals And Plan

## 1. What The Competition Is Asking You To Do

### Problem statement
- Build a binary classification model that predicts whether a player will be drafted into the NFL.
- Target column: `Drafted`
- Training data: `train.csv`
- Test data: `test.csv`
- Submission format: `sample_submission.csv`

### What a prediction means
- A prediction closer to `1` means the model believes the player is more likely to be drafted.
- A prediction closer to `0` means the model believes the player is less likely to be drafted.

### Evaluation metric
- The competition is scored by ROC-AUC.
- This means ranking quality matters more than choosing a hard cutoff like `0` or `1`.
- Your model should output probabilities, not final class labels.

### Submission rules that matter
- Submit a CSV with exactly these columns: `Id,Drafted`
- Use the same row order and IDs expected by `sample_submission.csv`
- Submissions with the wrong format get `-1`
- The public leaderboard is based on only part of the test set
- The private leaderboard is based on the full test set after the competition ends
- Final ranking is determined by your last submitted file
- Top participants may be asked to provide reproducible Google Colab code

### Hard constraints
- Do not use external data
- Do not manually label or hand-tune predictions for specific rows
- Predictions must be automatically generated by a reproducible model
- Set random seeds wherever possible
- If you reuse outside code, cite the source

### Important competition date
- `README.ipynb` says the competition ends on June 12, 2026 at 11:00 UTC
- In India time, that is June 12, 2026 at 4:30 PM IST

## 2. What Is In The Data

### Dataset size
- `train.csv`: 2781 rows, 16 columns
- `test.csv`: 696 rows, 15 columns

### Target balance
- Drafted `1.0`: 1803 players
- Not drafted `0.0`: 978 players
- The positive class is about 65 percent of the training set

### Feature groups
- Numeric athletic and body measurements:
  `Age`, `Height`, `Weight`, `Sprint_40yd`, `Vertical_Jump`, `Bench_Press_Reps`, `Broad_Jump`, `Agility_3cone`, `Shuttle`
- Categorical football context:
  `School`, `Player_Type`, `Position_Type`, `Position`
- Administrative:
  `Id`, `Year`

### Missing values you must handle
- `Age`: 435
- `Sprint_40yd`: 145
- `Vertical_Jump`: 554
- `Bench_Press_Reps`: 721
- `Broad_Jump`: 581
- `Agility_3cone`: 970
- `Shuttle`: 912

## 3. What The Baseline Notebook Is Teaching

### Baseline workflow
The baseline notebook does this:
- loads local CSV files
- runs basic EDA
- fills missing numeric values with train-column means
- drops `Id` and `School`
- label-encodes `Player_Type`, `Position_Type`, and `Position`
- trains a `RandomForestClassifier`
- evaluates with 5-fold stratified cross-validation using ROC-AUC
- adds one engineered feature: `BMI = Weight / Height^2`
- averages fold predictions to create submission probabilities

### Baseline result
- Baseline Random Forest AUC: about `0.8115`
- After adding BMI: about `0.8130`

### Key lesson from the baseline
- The notebook is not trying to give the best model.
- It is giving you a working pipeline and a valid first submission.
- Your real job is to improve features, preprocessing, and models while keeping evaluation disciplined.

## 4. What The Advanced Tutorials Add

The `advanced_techniques/` folder is a progression, not four unrelated examples.

### Tutorial 1: stronger baseline
Main ideas:
- compare feature sets one change at a time
- try count encoding for `School`
- add missing-value indicator columns
- compare models under the same CV split

Models explicitly compared:
- Logistic Regression
- Random Forest
- LightGBM

Main lesson:
- change one thing at a time and trust out-of-fold AUC, not leaderboard noise

### Tutorial 2: domain feature engineering
Main engineered features:
- `SPEED_SCORE = (Weight * 200) / Sprint_40yd^4`
- `EXPLOSIVENESS` from standardized `Vertical_Jump` and `Broad_Jump`
- `AGILITY_RATIO = Agility_3cone / Shuttle`

Also includes:
- optional SMOTE, applied inside training folds only

Main lesson:
- use football/combine meaning, not random feature creation
- lower sprint/agility times are better, so feature direction matters

### Tutorial 3: hyperparameter tuning
Main ideas:
- freeze the feature set first
- use CatBoost as the tuned model
- use Optuna to search hyperparameters
- compare tuned CatBoost against a default CatBoost baseline

Main lesson:
- tune after your features and CV pipeline are stable

### Tutorial 4: model ensembling
Main ideas:
- train multiple strong models on the same feature set
- compare their out-of-fold predictions
- combine predictions by:
  `equal average`
- and:
  `rank average`

Models explicitly used:
- AdaBoost
- XGBoost
- LightGBM
- CatBoost

Main lesson:
- ensembles help only when strong models make somewhat different ranking errors

## 5. Clear Understanding Of The Goal

Your goal is not just to make a submission.

Your actual goal is:
- create a reproducible local pipeline
- produce a valid first leaderboard score quickly
- improve cross-validated ROC-AUC before chasing submissions
- submit only changes that are supported by validation
- finish with one strong final submission as your last upload before the deadline

If you want to be ahead on the leaderboard, the winning behavior is usually:
- fewer random experiments
- better validation discipline
- stronger features
- stronger boosting models
- a careful ensemble at the end

## 6. Recommended Strategy To Stay Ahead Of The Leaderboard

### High-level strategy
1. Get on the leaderboard fast with the baseline
2. Build a stronger validation pipeline locally
3. Improve preprocessing and feature engineering
4. Compare stronger model families
5. Tune only the best few candidates
6. Ensemble only the strongest diverse models
7. Keep the final submission for your best validated result

### What not to do
- Do not spam many leaderboard submissions without CV evidence
- Do not trust tiny public leaderboard gains by themselves
- Do not change features and models at the same time if you want to know what helped
- Do not leak test information into preprocessing
- Do not fit imputers or scalers using test data statistics

## 7. Step-By-Step Plan You Can Follow

### Phase 1: establish the baseline
1. Run `baseline.ipynb` fully
2. Confirm it creates a valid `submission.csv`
3. Submit once to get your initial public score
4. Save the score, notebook version, and submission timestamp in your notes

### Phase 2: build your experiment log
1. Create a simple table with:
   `experiment name`, `features`, `preprocessing`, `model`, `CV AUC`, `public score`, `notes`
2. Record every change
3. Never rely on memory for which version was better

### Phase 3: improve preprocessing first
1. Keep the same CV split and seed across experiments
2. Add missing-value indicator columns
3. Try better missing-value handling:
   `median`
4. Then try:
   group-wise fill by position
5. Try keeping `School` using count encoding first
6. Compare label encoding vs one-hot or frequency-style approaches for low-cardinality categoricals

### Phase 4: improve features
1. Keep BMI
2. Add `School` count encoding
3. Add missing indicators
4. Add domain features from Tutorial 2:
   `SPEED_SCORE`, `EXPLOSIVENESS`, `AGILITY_RATIO`
5. Test one new feature at a time, then combined sets
6. Keep only features that improve out-of-fold AUC consistently

### Phase 5: compare models
1. Start with the best feature set from Phases 3 and 4
2. Compare:
   Logistic Regression
3. Compare:
   Random Forest
4. Compare:
   LightGBM
5. Compare:
   CatBoost
6. Compare:
   XGBoost
7. Rank them by out-of-fold AUC, not by intuition

### Phase 6: tune only the top candidates
1. Pick the best 1 or 2 models from Phase 5
2. Tune their hyperparameters
3. Use Optuna or a small targeted search
4. Keep the same feature set while tuning
5. Watch for overfitting:
   if CV improves only by a tiny amount and leaderboard becomes unstable, stop tuning

### Phase 7: build an ensemble
1. Keep only strong individual models
2. Check whether their out-of-fold predictions are different enough
3. Try:
   equal average
4. Try:
   rank average
5. Compare ensemble AUC against the best single model
6. Submit the ensemble only if CV says it is better

### Phase 8: final submission management
1. Before the deadline, identify your strongest validated submission
2. Make sure it is reproducible from notebook start to finish
3. Upload that version last, because the last file determines final rank
4. Keep the exact code and package list ready in case reproducibility is checked

## 8. Best Practical Order Of Work

If time is limited, use this order:

5. LightGBM and CatBoost comparison

8. Final submission

What you need to do is simple in structure:
